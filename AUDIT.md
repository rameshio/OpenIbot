## Six-plane map

### 1. Cognition — models and prompts

**Exists:** native Responses, Messages, and OpenAI-compatible chat adapters; tool-call conversion; screenshot messages; model discovery with catalog metadata; provider retries/timeouts and sanitized HTTP errors. Bot role, user instructions, memory, installed skills, connector catalogs, time, roster, and policy rules are composed into the system prompt. Models lacking tool support receive a limited tool-free path. Media generation/transcription are separate user-facing operations. Evidence: `desktop/providers.ts:4–9`, `desktop/providers.ts:34–96`, `desktop/providers.ts:98–159`, `desktop/engine.ts:129–132`, `desktop/engine.ts:209–213`, `desktop/media.ts:12–49`.

**Missing:** prompt/version identifiers in saved usage; token-aware context compaction; durable provenance and trust separation for memory/skills; deterministic authorization derived from user intent. The prompt says external content is untrusted, but bot memory and skill text are inserted directly into privileged context. Restart history uses the last 100 visible messages, not a token budget or original typed transcript. Evidence: `desktop/engine.ts:129–132`, `desktop/engine.ts:157–159`, `desktop/engine.ts:212–213`, `desktop/engine.ts:255–255`, `shared/types.ts:20–22`. Model quality, context limits in practice, and resistance to prompt injection are **UNKNOWN**.

### 2. Orchestration — loops, sub-agents, routing

**Exists:** per-chat loops, cancellation, per-bot ownership, shared model-turn budget, delegation depth limit, specialist creation, explicit handoffs, and concurrent delegate batches of at most three. Chief starts as coordinator. A verifier can review tool-based work before the coordinator delivers the answer. A run retains its starting model/key even when the user changes provider settings. Evidence: `desktop/store.ts:8–15`, `desktop/engine.ts:21–29`, `desktop/engine.ts:145–155`, `desktop/engine.ts:205–232`, `desktop/engine.ts:235–277`, `tests-desktop/providers.test.ts:189–200`.

**Missing:** durable run/task graph and delegation checkpoints, individual specialist model routing, persisted action IDs and replay protocol, guaranteed independent review, deterministic enforcement of a failed review. Review is another model response; it can be skipped when budgets/slots are exhausted. Its tool list still includes shell, computer, connector, file writes, memory, and skills. Evidence: `desktop/engine.ts:211–211`, `desktop/engine.ts:258–272`, `shared/types.ts:6–8`, `shared/types.ts:20–22`.

### 3. Execution — tools, shell, browser, connectors

**Exists:** bot creation/delegation; file list/read/write/share; shell; screenshots; pointer/keyboard control; browser URL opening; memory/skill/routine writes; MCP tool invocation. Shell execution occurs in labelled per-bot containers as UID 1000, with dropped capabilities, no-new-privileges, CPU/memory/PID limits, separate network/home/work volumes, and only a loopback noVNC port published. Host Docker calls use argument arrays and `shell:false`. File access uses a pinned `/workspace` root and rejects traversal, symlinks, hard links, and nonregular files. Evidence: `desktop/engine-tools.ts:5–27`, `desktop/runtime.ts:54–58`, `desktop/runtime.ts:141–145`, `desktop/runtime.ts:202–235`, `desktop/runtime.ts:277–349`, `containers/workspace_files.py:16–90`.

**Exists, connectors:** HTTP MCP with tool discovery, assigned-bot checks, bearer tokens or OAuth, PKCE verifier handling, random callback state, loopback callback, scoped persisted tokens, and redirect rejection. Evidence: `desktop/engine.ts:135–137`, `desktop/engine.ts:160–165`, `desktop/engine.ts:398–409`, `desktop/connectors.ts:5–35`, `desktop/connectors.ts:38–65`.

**Missing:** destination-aware egress restrictions; per-tool capability grants; mediation of credential access within the bot home; an inner Chromium sandbox; host-crash reconciliation of running commands. `/workspace` confinement applies to the file bridge, not shell. A shell process can access the bot's home and network. Evidence: `containers/run_command.py:41–52`, `containers/entrypoint.sh:24–26`, `desktop/runtime.ts:223–229`. Remote MCP server implementation, granted account permissions, and externally enforced network restrictions are **UNKNOWN**.

### 4. State — memory, history, schedules

**Exists:** `state.json` holds bots, editable memory, chats/messages, skills, routines, approvals, usage, and settings; ciphertext secrets and routine slot markers live alongside it. Save writes a flushed temporary file, makes a backup, then renames. Docker volumes persist workspace and browser home. The scheduler checks every 15 seconds with timezone/day validation and persisted slot deduplication; missed schedules are deliberately not backfilled. **Missing:** action journal/checkpoints, memory revision/provenance/rollback, automatic backup recovery, comprehensive stored-state schema validation, retention/size limits, and durable job queue. Only version/bots/chats receive initial structural checks. Every publish rewrites the whole snapshot and backup. Schedules can be skipped when a bot is busy. Evidence: `desktop/store.ts:28–35`, `desktop/store.ts:65–69`, `desktop/engine.ts:33–38`, `desktop/engine.ts:157–159`, `desktop/engine.ts:286–301`. Crash-consistent coordination between JSON state, Docker volumes, and external side effects is **UNKNOWN**.

IPC checks window identity, main frame, trusted URL, command allowlist, and input size. Electron uses context isolation, sandboxing, and no Node integration. ### 6. Control — approvals, policies, audit, egress

**Exists:** central `authorize()` for model tools in four classes: shell, computer, browser, connector. Block takes precedence; ask waits for a user decision; otherwise allow or disabled autoReview permits execution. Pending approvals are denied on cancellation/restart. Exact action classes and `*` are mechanically enforced; natural-language rules are advisory. Defaults enable review. UI provides rule editing and approve/decline. Evidence: `desktop/engine.ts:112–123`, `desktop/engine.ts:164–165`, `desktop/engine.ts:179–198`, `desktop/engine.ts:281–284`, `desktop/engine.ts:328–338`, `desktop/engine.ts:394–396`, `desktop/store.ts:15–15`, `desktop/store.ts:55–62`, `renderer/Settings.tsx:92–93`.

**Exists:** visible activity messages record handoffs and tool output; usage records model/provider/token counts. Renderer CSP and IPC/window hardening constrain renderer access. Provider/MCP HTTP redirects are refused. Evidence: `desktop/engine.ts:36–38`, `desktop/engine.ts:153–155`, `desktop/engine.ts:212–222`, `renderer/index.html:2–2`, `desktop/main.ts:34–38`, `desktop/main.ts:74–79`, `desktop/providers.ts:24–39`, `desktop/connectors.ts:20–23`.

**Missing:** universal outbound-action enforcement; semantic policies for send/delete/spend/upload; policy version binding and revalidation after approval; complete append-only action/decision audit with run IDs and redaction; independent network enforcement. File writes/shares, memory/skills/schedules, and model traffic do not pass through `authorize()`. Trusted user IPC paths deliberately execute terminal/file operations directly; no model-to-IPC escape was established. Evidence: `desktop/engine.ts:157–177`, `desktop/engine.ts:211–213`, `desktop/main.ts:111–141`, `shared/types.ts:8–12`, `shared/types.ts:20–22`.

## Recommended build order for Claude

1. **Define effect contracts and centralized authorization (gap 3).** Inventory every model, tool, media, connector, shell, browser, and IPC effect. Preserve intentional user control while identifying the initiating actor. Introduce target/data/policy-version-bound grants and deny unclassified agent effects. Acceptance: blocking an effect remains effective across transports; policy changes invalidate pending grants.
2. **Move credentials behind a broker and restrict egress (gaps 1–2).** Separate agent execution from browser/session secrets and vault runtime credentials. Enforce destinations outside the shell/container. Acceptance: a permitted agent script cannot read broker secrets, and unapproved destinations/uploads fail through shell, browser, and connectors.
3. **Gate durable behavior changes (gap 4).** Add reviewable memory/skill revisions, provenance, and explicit schedule authorization. Acceptance: untrusted task content cannot silently install future instructions or recurring work.
4. **Build durable run/action state and supervise execution (gaps 5–6).** Introduce stable run/action IDs, typed transcripts, approval/dispatch/outcome journaling, uncertain-outcome reconciliation, and job leases. Acceptance: forced termination at each action boundary yields a recoverable run without automatic duplicate effects or orphaned jobs. Do not promise exactly-once behavior for services without idempotency/reconciliation support.
5. **Add independent audit and read-only verification (gaps 7–8).** Persist sanitized route/action/policy events separately from chat; restrict reviewer tools and enforce configured completion checks. Acceptance: every action is attributable to a run, actor, grant, target, and result; failed required checks prevent successful completion.
6. **Harden storage and make verification repeatable (gaps 9–10).** Add full schema migration/recovery, bounded history, and backup restoration; align test commands with the active app. Add the relevant regression tests alongside each earlier step, then require Windows/Docker boundary and forced-crash checks before release. Acceptance: corrupt/oversized state and interrupted writes have documented recovery behavior, and verification records identify the tested source/package.
